# MCP (Model Context Protocol)

`mcp.json` хранит конфигурацию опциональных MCP-серверов и сохранённое состояние встроенных инструментов. Путь к файлу задаётся через `MCP_CONFIG_PATH` (по умолчанию `mcp.json`). Переменные окружения в строковых значениях конфигурации раскрываются при загрузке.

В текущем шаблоне доступны `context7` (remote HTTP, read-only, включён) и `sequential-thinking` (stdio, выключен). Поле `enabled` управляет загрузкой сервера. После ручного изменения конфигурации перезапустите приложение; UI сохраняет состояние в этот же файл.

Служебный объект `_builtin_tools` не является MCP-сервером. UI записывает в него пользовательские overrides для встроенных инструментов, например `"download_file": false`. Если override отсутствует, состояние определяется соответствующим feature flag из `.env`.

## Policy

Поддерживается только флаг `policy.read_only`. Его можно задать для всего сервера и переопределить для отдельного инструмента через `policy.tools.<tool_name>.read_only`.

- `true`: инструмент считается read-only и не требует approval.
- `false`: инструмент считается изменяющим состояние и требует approval.
- Флаг не указан: агент использует MCP metadata hints; если сервер не предоставил достаточные hints, применяется консервативный режим с approval.
- `ENABLE_APPROVALS=false`: глобально отключает запросы approval независимо от MCP policy.

Пример policy для отдельного инструмента:

```json
{
  "example-server": {
    "transport": "stdio",
    "command": "example-mcp-server",
    "enabled": true,
    "policy": {
      "read_only": true,
      "tools": {
        "update_record": {
          "read_only": false
        }
      }
    }
  }
}
```

## Сжатие вывода

Для MCP не нужны отдельные параметры сжатия в `mcp.json`. Инструмент определяется по runtime metadata `source == "mcp"`, а общий pipeline управляется параметрами `ENABLE_HEADROOM_COMPRESSION` и `MAX_TOOL_OUTPUT` из `.env`.

1. Результаты типа `dict` и `list` сериализуются в JSON через `json.dumps(..., ensure_ascii=False)`. Строковые результаты сохраняются как есть.
2. Ответ размером не больше `MAX_TOOL_OUTPUT` передаётся модели без сжатия.
3. Для большего ответа при `ENABLE_HEADROOM_COMPRESSION=true` вызывается `ContentRouter` — тот же движок, что и для остальных инструментов. Он сам определяет тип содержимого (JSON-массив, табличные данные, лог, текст) и выбирает компрессор.
4. Роутер не знает про бюджет `MAX_TOOL_OUTPUT` и может остановиться после небольшой lossless-упаковки. Если результат вместе со служебным footer превышает бюджет или отклонён проверкой качества, дополнительно вызывается `LogCompressor` — только для логов, то есть когда роутер отнёс содержимое к логу либо распознан конкретный формат сборки или тестов. Его лимиты (сколько ошибок, предупреждений, стеков и строк сохранять) считаются от `MAX_TOOL_OUTPUT`. Сначала проверяется вариант с дедупликацией предупреждений; вариант без неё вычисляется только при отклонении первого. Для обычного текста повторный log-проход не выполняется.
5. Принимается непустой результат без неразрешимого retrieval marker, который сохраняет диагностику и исходный статус `ERROR[TYPE]`. Служебный footer учитывается в размере: результат вместе с ним должен быть меньше исходного. Если результат роутера пригоден и помещается в бюджет, он принимается сразу, за исключением случая с логами: в headroom 0.38 роутер может вернуть лог без дедупликации, поэтому такой результат всё равно проверяется через log-проходы, чтобы найти более короткий вариант с дедупликацией. Если результат роутера непригоден или слишком велик, из пригодных результатов роутера и log-прохода берётся более короткий.
6. После семантического этапа результат в любом случае ограничивается до `MAX_TOOL_OUTPUT`.

Текущий агент не регистрирует инструмент `headroom_retrieve`, поэтому CCR-указатели (`<<ccr:...>>`, `Retrieve more: hash=`, `Retrieve original: hash=`) были бы бесполезны для модели. CCR отключён в конфигурации роутера, а проверка маркеров оставлена как страховка. При passthrough, ошибке, недоступности Headroom или найденном маркере агент применяет детерминированный fallback: сохраняет начало и конец ответа, а удалённую середину отмечает как `[OMITTED N chars]`.

Проверка диагностики из пункта 5 отсекает вырожденные результаты. Диагностические строки (ошибки, предупреждения, traceback) сравниваются по токенам, а не целиком, поэтому переупакованные записи (JSON-объекты в CSV-строки) считаются сохранёнными. Кандидат сравнивается с детерминированным сокращением того же содержимого, причём оба измеряются в том виде, в котором их получит модель: если сжатие доносит меньше диагностики, чем простое сокращение, оно отклоняется, а когда ошибок больше, чем вмещает бюджет, выигрывает вариант, доносящий их больше. Диагностика исходного ответа и результат его детерминированного сокращения подготавливаются один раз на вызов и переиспользуются для проверки кандидатов. Когда диагностики нет, полезная часть результата (без footer) должна занимать не менее четверти бюджета `MAX_TOOL_OUTPUT`, чтобы не принять маркер вида `[N lines omitted]` вместо данных. Исключение — явно подтверждённая Headroom lossless-цепочка (`strategy_chain` состоит только из `lossless_*`): точное сворачивание тысяч одинаковых строк принимается даже при очень маленьком результате. Смешанная lossless/lossy-цепочка это исключение не получает.

## Удалённый сервер

```json
{
  "context7": {
    "type": "remote",
    "url": "https://mcp.context7.com/mcp",
    "transport": "http",
    "enabled": true,
    "policy": {
      "read_only": true
    }
  }
}
```
