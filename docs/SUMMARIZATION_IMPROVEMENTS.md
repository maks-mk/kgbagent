# Рекомендации по улучшению суммаризации

Статус: план дальнейших улучшений, а не описание реализованных изменений.

Цель — сохранять сведения, необходимые для продолжения задачи, при ограниченном размере памяти и приемлемой стоимости запросов. Сжатие с потерями не может гарантировать сохранение всех важных деталей; качество нужно проверять на сценариях продолжения работы, а не только по длине результата.

## 1. Что уже реализовано

- Кодовый дефолт `SESSION_SIZE` увеличен до `40000`. Реальный порог может быть переопределён конфигурацией; `.env` при этом изменении не менялся.
- Длинный результат `ToolMessage` в представлении истории для суммаризатора сокращается по схеме «начало + конец»: около 30% доступного места под начало и 70% под конец. Лимит — 500 символов вместе с маркером ` ... [truncated] ... `.
- Пробельные символы нормализуются в одну строку. Короткий результат не обрезается, но также проходит эту нормализацию.
- Для остальных сообщений пока сохраняются первые 500 символов плюс маркер. Представление списка вызовов инструментов, включая имена и аргументы, ограничивается первыми 320 символами плюс маркер.
- Добавлены регрессии на ошибку и итоги тестов в хвосте, короткий и структурированный вывод, неизменность форматирования обычных сообщений и аргументов.

Это форматирование применяется к части истории, выбранной для удаления из рабочего контекста. Оно не заменяет основной вывод инструмента. Суммаризация удаляет сообщения из `messages`, но сохраняет историю сообщений в `transcript_messages`. Если вывод был сокращён ещё до создания сообщения, наличие transcript не восстанавливает исходный вывод.

Запрос суммаризатора содержит предыдущую память, выбранную часть истории и operational snapshot: текущую задачу, открытую проблему инструмента, стратегию восстановления и внешний блокер при их наличии. Основной системный промпт агента, схемы инструментов и весь архив переписки в этот запрос не добавляются. Внутренние retry-сообщения и структурированные provider reasoning-блоки исключаются из текстового представления истории.

Границы сжатия учитывают пользовательские ходы и завершённые раунды инструментов. Сжатие возможно и внутри активного хода после tools/recovery; нельзя считать весь текущий ход безусловно защищённым от суммаризации.

## 2. Основные оставшиеся риски

- Важная ошибка, путь или решение могут находиться в середине длинного вывода и не попасть ни в начало, ни в конец.
- Фрагменты начала и конца могут относиться к разным операциям. Например, успешная очистка временных файлов в хвосте не означает успешную сборку.
- Нормализация пробелов разрушает структуру traceback, многострочного кода и некоторых диагностик.
- Вывод может сокращаться дважды: сначала общим компрессором инструментов, затем форматтером суммаризации. Отобранная первым этапом диагностика может быть потеряна на втором.
- Длинные пользовательские ограничения и значимые аргументы инструментов всё ещё могут обрезаться до начала строки. При нескольких вызовах последние вызовы могут исчезнуть из ограниченного представления списка.
- При многократной суммаризации ошибки памяти накапливаются: исчезают оговорки, предположения превращаются в факты, устаревшие итоги вытесняют актуальные.
- Слишком большой бюджет памяти увеличивает последующие запросы, слишком маленький — потери деталей и повторную работу. При превышении бюджета возможны дополнительный вызов fold и жёсткая обрезка.

## 3. Высокий приоритет: сохранить диагностические факты

### 3.1. Создать небольшой корпус регрессионных сценариев

До изменения алгоритма зафиксировать текущий вариант «начало + конец» как базовый для сравнения. Для каждого примера задать конкретные факты, необходимые для следующего шага, и проверить, дошли ли они до представления истории и итоговой памяти.

Минимальный набор:

- Ошибка в начале, середине и конце вывода; после ошибки — длинный прогресс или успешная вспомогательная операция.
- Итоги успешных, неуспешных и частично пропущенных тестов; отдельно — тесты вообще не запускались.
- Traceback, несколько ошибок, предупреждение без ошибки, ненулевой exit code без слова `ERROR`.
- JSON-результат с вложенным статусом, путём артефакта и сообщением об ошибке; многострочный и однострочный варианты.
- Несколько параллельных вызовов одного инструмента с разными аргументами и противоположными результатами.
- Длинная задача с ограничением в конце, затем «продолжай»; смена задачи; противоречащие друг другу старые и новые результаты.
- Несколько последовательных циклов summary/fold, включая ошибку или пустой ответ суммаризатора.

**Критерий:** все обязательные факты сценария сохраняются либо явно отмечаются как неизвестные; сжатый результат не создаёт ложного подтверждения успеха. Для заведомо недостаточного бюджета отдельно фиксируется ожидаемая потеря, а не обещается невозможное сохранение всего.

### 3.2. Перейти от слепой обрезки к отбору фактов в том же бюджете

Для известных форматов результатов рассмотреть схему «идентификация операции + диагностические строки + итог». Приоритетные сведения:

1. Фактический статус и exit code, если они явно присутствуют.
2. Неустранённая ошибка и контекст, необходимый для исправления: путь, идентификатор, краткая причина.
3. Итоги проверок, включая failed/skipped и ограничения проведённой проверки.
4. Значимые артефакты и следующий необходимый шаг, если он явно указан в результате.
5. Общий контекст из начала и конца — на оставшееся место.

Сначала изучить и по возможности переиспользовать правила из `core/tool_output_compressor.py`: там уже есть отбор диагностик, обработка структурированного вывода и детерминированный reducer. Не подключать весь компрессор автоматически к каждому сообщению: его бюджеты и назначение отличаются. Общие правила выделять только при подтверждённой необходимости, без второй независимой системы распознавания ошибок.

Для неизвестного, повреждённого или неоднозначного формата оставить текущий head+tail как резервный вариант. Отбирать строки до нормализации пробелов. Маркер должен показывать пропуск, а не склеивать фрагменты в якобы непрерывный текст.

**Компромисс:** диагностика занимает место общего контекста; поиск по ключевым словам может принять пример ошибки за реальную ошибку. Нельзя выводить успех из отсутствия слова `ERROR` или подменять статус операции статусом последней строки.

**Критерий:** на корпусе при прежнем лимите сохраняются диагностические факты из середины без регрессий по хвосту. Отдельный интеграционный тест проходит всю цепочку «компрессор результата → ToolMessage → форматтер → суммаризатор».

### 3.3. Сохранять связь между вызовом и результатом

При нескольких вызовах имя инструмента само по себе недостаточно. Рассмотреть компактную привязку результата к вызову через имеющийся `tool_call_id` либо однозначную локальную метку, а также выбор значимых аргументов вместо обрезки всего списка вызовов на 320 символах.

Для известных инструментов приоритетны команда, путь, запрос и параметры, меняющие смысл операции. Не переносить в память секреты из аргументов и не добавлять полные аргументы каждого вызова без ограничения размера.

**Критерий:** суммаризатор не приписывает ошибку или успех соседнему вызову; отсутствие части аргументов отмечается как сокращение. Границы рабочих tool-round и пары вызов/результат остаются корректными.

## 4. Средний приоритет: качество и устойчивость памяти

### 4.1. Проверять содержание, а не только размер

Текущий prompt уже требует сохранять задачу, прогресс, блокеры, точные идентификаторы и неопределённость. Прежде чем добавлять новые инструкции, проверить выполнение этих требований на корпусе.

Если обнаружатся устойчивые пропуски, уточнить компактный формат памяти: цель и ограничения; подтверждённые результаты; открытые проблемы; решения и следующие шаги. Не вводить обязательную JSON-схему или новый слой хранения без доказанной потребности.

Особое внимание:

- Различать «запланировано», «попытка выполнена» и «успех проверен».
- Сохранять запреты пользователя, нерешённые вопросы и ограничения проверок.
- Обновлять устаревшие результаты только при наличии новых относящихся к ним свидетельств.
- Не принимать инструкции внутри логов или документов за команды суммаризатору.

**Критерий:** после нескольких циклов сжатия агент продолжает нужную задачу, не повторяет уже выполненные операции без причины и не заявляет о непроведённых проверках.

### 4.2. Уменьшить дублирование текущей задачи без потери цели

Полная текущая задача передаётся в operational snapshot и может повторяться в истории или памяти. Измерить долю такого повторения во входе суммаризатора.

Безопасный первый вариант — устранять только точные дубликаты, если полная актуальная задача действительно присутствует в отправляемом представлении. Наличие исходного сообщения в истории недостаточно: форматтер мог уже обрезать его. Смысловую дедупликацию и произвольное сокращение требований отложить до отдельных проверок качества.

**Критерий:** команды «продолжай» не теряют исходную цель, новые ограничения не вытесняются старыми, хвост длинного задания сохраняется хотя бы в одном источнике запроса.

## 5. Средний приоритет: стоимость и бюджеты

### 5.1. Измерять фактические затраты

Расширять существующие события `summary_compacted` и `summary_memory_folded`, а не создавать параллельную систему логирования. Полезные показатели:

- Оценка токенов предыдущей памяти, истории и snapshot по отдельности.
- Размер памяти после сжатия, частота fold и жёсткой обрезки.
- Число вызовов и задержка суммаризации; при доступности — фактические usage-данные провайдера.
- Частота повторных действий и уточнений, вызванных потерей сведений.

Не логировать содержимое команд, аргументов и памяти ради подсчёта размера. Различать локальную оценку токенов и тарифицируемое usage: они не обязаны совпадать.

### 5.2. Подбирать бюджет памяти по измерениям

Сейчас `SUMMARY_MAX_TOKENS=0` означает автоматический бюджет в четверть `SESSION_SIZE`. При кодовом дефолте `40000` это `10000` токенов. Это верхняя граница, а не фактический размер каждого summary и не лимит генерации провайдера.

Сравнить текущий авто-бюджет с несколькими меньшими явными бюджетами на одинаковых задачах. Оценивать суммарную стоимость: запросы суммаризатора, передача памяти основному агенту, дополнительные fold и повторная работа из-за потерь.

Не уменьшать одновременно порог, бюджет и настройки модели: иначе причину изменения качества будет трудно установить. Не убирать fold без замены механизма ограничения памяти. Проверить сохранение приоритетных фактов и при его сбое с последующей жёсткой обрезкой.

**Критерий:** затраты или задержка снижаются без ухудшения прохождения выбранных сценариев продолжения задачи. Точный бюджет выбирать по результатам, а не объявлять универсальным.

### 5.3. Настройка reasoning текущей модели — только после оценки качества

Узел вызывает `self.llm`. Возможный эксперимент — менее затратный режим reasoning текущей модели для запросов суммаризации, если это поддерживает используемый провайдер.

До реализации проверить API и допустимые настройки по установленным версиям и официальной документации. Не менять режим основного агента ради суммаризации. Оценивать точность переноса фактов, путей и команд, задержку и затраты.

**Критерий:** сравнение на одном корпусе показывает экономию при приемлемой сохранности обязательных фактов. Живые API-прогоны требуют отдельного согласования затрат и передачи данных; mock-тесты не подтверждают качество модели.

## 6. Что пока не стоит усложнять

- Не увеличивать общий лимит вывода только для компенсации неудачного отбора фрагментов.
- Не заменять все сокращения дополнительными LLM-вызовами: это повышает стоимость, задержку и число точек отказа.
- Не добавлять retrieval по архиву, векторную базу или отдельное хранилище фактов до подтверждения потребности. Transcript полезен для проверки, но не становится автоматически доступной памятью модели.
- Не менять формат обычных сообщений, аргументов, настройки reasoning и бюджеты одним пакетом. Для каждого изменения нужны отдельные регрессии.
- Не считать сохранённый хвост доказательством сохранения всей важной информации.

## 7. Рекомендуемый порядок внедрения

1. Зафиксировать корпус, обязательные факты и исходные показатели текущего head+tail.
2. Проверить двойное сокращение и улучшить отбор диагностик в прежнем бюджете, переиспользуя существующие правила.
3. Закрыть неоднозначность нескольких вызовов и потери значимых аргументов.
4. Проверить многократные summary/fold, пользовательские ограничения и дублирование задачи.
5. Измерить токены и задержки, затем отдельно подобрать бюджет памяти.
6. Только после этого оценивать другой reasoning-режим текущей модели для суммаризации.

На каждом шаге: небольшое независимое изменение, профильные тесты, интеграционные проверки затронутой цепочки и сравнение с исходным вариантом. Для чисто детерминированного форматирования дополнительные API-вызовы не нужны; для качества итоговой памяти одних проверок форматтера недостаточно.
